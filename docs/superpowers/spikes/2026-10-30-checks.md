ZeroSub was installed and running (revision
`0012a789fb7874f85b0ad4ac9852a77e52deb9eb`), but **this API returned no ZeroSub
entry**, and no duplicate Claude or Codex provider entries.

**Can a report describe a different account than an agent uses? Yes, the
available API does not rule this out.** The observed report is provider-wide and
has no agent or session account binding. Inspection of the installed ZeroSub
source, without reading credentials or its account state, establishes that it
routes each session through `agent.session_open` and supplies account-specific
environment patches. `server/service.ts:421` applies the selected account's
environment; `server/claude.ts:64-67` selects `CLAUDE_CONFIG_DIR`, and
`server/codex.ts:206-207` selects `CODEX_HOME`. These are source references, not
environment values read from an agent.

This proves a structural attribution risk; it does **not** claim that either
sampled agent actually uses a different account. No such account comparison was
attempted. One report per provider is insufficient evidence of an account match.
The spec's duplicate-report guard therefore cannot prevent every wrong-account
value. Stop before building usage widgets and obtain Simon's decision about
account attribution or explicitly labelled provider/account-wide values.

There is also a type mismatch in the plan: in 0.13.2,
`PaseoProviderUsageResult["providers"][number]` is the legacy provider shape above.
The separate protocol `UsageReportEntry` has `sourceId`, `sourceLabel`, `account`,
and nested `report`; it does not have `providerId`. Task 3's proposed
`selectUsage(reports: UsageReportEntry[], provider: string)` needs correction or
an explicit conversion. Do not silently treat these as the same contract.

## Check 3: recent skill timeline shape

Read recent timelines with the SDK, without sending an agent prompt or calling
`commands()`. This diagnostic read is a Task 1 exception to the eventual
popover-open-only runtime rule. The helper prints tool shapes and explicit Skill
details, not general command arguments, file contents, or tool output.

The response envelope has `entries`, with each timeline item in `entry.item`.
It also has paging fields including `startCursor`, `endCursor`, `hasOlder`, and
`hasNewer`.

### Claude

Agent `29ce902d-f665-42b3-a365-12a82f0d6e30`; 100 recent entries sampled.
Found an explicit shape suitable for identifying skill use:

```json
{
  "type": "tool_call",
  "callId": "<call ID omitted>",
  "name": "Skill",
  "detail": {
    "type": "plain_text",
    "label": "superpowers:writing-plans",
    "icon": "sparkles",
    "text": "Launching skill: superpowers:writing-plans"
  },
  "status": "completed",
  "error": null
}
```

An earlier item had the same shape with `detail.label: "paseo"` and
`detail.text: "Launching skill: paseo"`. The newer observed skill was
`superpowers:writing-plans`. Match the explicit `name: "Skill"` and the
`plain_text` detail; the name is in `detail.label`. There was no input object in
these Skill items. Do not invent an `input.skill` field.

### Codex

Agent `0a647925-7650-4552-a34c-063f194dd4fd`; 53 recent entries on the final read.
No explicit skill-use marker was found. Ordinary calls had `type: "tool_call"`,
`name: "shell"`, and `detail` keys `type`, `command`, `cwd` plus optional
`output` and `exitCode`. Other calls included `terminal`, `agent_message`, and
Paseo browser tools. These do not reliably identify a used skill. Reading a
SKILL.md through a shell command does not prove invocation. Hide Codex's skill
widget unless a reliable explicit shape is established later. This is a bounded
sample result, not a claim about every Codex timeline.
